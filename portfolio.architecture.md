## 12. Known Quirks and Gotchas

- **`output: "export"`** (`next.config.ts:4`) means no Server Actions, no API routes, no `revalidate`, no `dynamic = "force-dynamic"`, no `use cache` will work in this project. Any future server-side feature requires removing static export first.
- **Both pages are Client Components** (`"use client"` at the top of `page.tsx` and `portfolio/page.tsx`). This is required because `PageShell` calls `posthog.capture(...)` on click; the entire page tree therefore ships to the browser. There is no Server Component / Client Component boundary to be careful about.
- **Static export interaction with PostHog**: `posthog-setup-report.md:10` notes the reverse-proxy pattern was skipped because of `output: "export"`. Events hit `us.i.posthog.com` directly — be aware ad-blockers will eat them.
- **`NEXT_PUBLIC_POSTHOG_PROJECT_TOKEN!` non-null assertion** in `instrumentation-client.ts:3` will pass `undefined` to PostHog if the env var is missing in a build environment, rather than failing fast. Watch this on first preview deploys.
- **`tsconfig.json:33` excludes `"sites"`** — the host build does not see the sub-projects at all. If you `import` from `sites/...` in the host, TypeScript will not type-check it. (Currently nothing does.)
- **`out/` and `.next/`** are present in the working tree but gitignored. The static-export `out/` includes a `__next.__PAGE__.txt`, `__next._full.txt`, etc., which are Next 16 debug artifacts — fine to delete.
- **`.claude/skills/integration-nextjs-app-router/`** is a PostHog-shipped agent skill folder noted in `posthog-setup-report.md:36`. It influences Claude Code behavior in this repo but is not part of the deployed app.
- **Tailwind v4 has no `tailwind.config.{js,ts}`** in this repo — Tailwind v4 reads configuration from CSS (`@import "tailwindcss"`). Don't go looking for a config file.
